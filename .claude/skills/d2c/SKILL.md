# D2C

## 目标与边界

把 Figma URL 中明确的节点实现到现有 Web 前端项目。以结构化设计信息和当前项目证据为依据，优先复用项目组件、Token、主题、资源与业务模式；修改业务代码前必须让用户确认实现预览。

首版实际验证范围是 React + TypeScript 和 Vue 3 + TypeScript；这不是流程的硬限制。其他可识别的现有 Web 前端项目也按相同证据链执行，但交付时要如实说明尚未经过本项目基准验证。

这个 Skill 只编排当前会话中的读取、判断、写入和验证：

- 不安装、启动或认证 MCP。仅在目标项目缺少 `.mcp.json` 时，可从随 Skill 分发的无凭据模板创建该文件；不覆盖已有配置。允许检查配置是否存在、Provider 是否配置及认证状态；不得读取、输出或保存 OAuth、Token、环境变量等凭据值。
- 不创建运行脚本、状态机、`.d2c` 工作区、manifest、normalized JSON、阶段报告或独立日常预览工程。
- 除“未显式指定 Provider 且默认官方 Provider 返回 OAuth 未授权、授权被拒绝或授权已过期”外，不自动切换 Provider；任何切换都不混用两个 Provider 的结果。不自动评分或循环收敛。
- 不支持从 Figma Desktop 当前选择推断目标，也不允许只看截图猜代码。

Provider 指取得 Figma 证据的工具来源。本 Skill 仅支持当前会话中实际可调用的官方 Figma MCP 或 Figma-Context-MCP。

## 固定流程

每次向用户显示并遵守这个顺序：

```text
MCP config → preflight → provider → design context → project rules → project analysis
→ implementation preview → confirmed write → engineering validation
→ visual review → delivery
```

不得跳过前置停止条件或两个确认点。小组件可以缩短预览内容，但不能改变顺序。

## 硬停止条件

遇到以下任一条件，说明缺失项并停止，不写对应项目规则或业务代码：

- Figma URL 缺少具体 `node-id`：要求用户提供目标节点；不得浏览整份文件猜主 Frame。
- 目标目录不存在，或不能从项目文件识别为现有 Web 前端项目。
- 本轮刚创建 `.mcp.json`，尚未由用户完成本地配置并重启 Claude。
- 用户显式选择的 Provider 在当前会话中缺少完成本任务所需的可调用工具。
- 没有取得目标节点的结构化设计上下文；截图不能替代它。
- 项目首次使用且 `D2C.md` 候选内容尚未得到用户确认：不得写入 `D2C.md`，也不得继续业务实现。
- 实现预览尚未得到用户确认，或用户调整后更新的预览尚未再次确认：不得修改业务代码。

## 1. Preflight

1. 目标项目使用用户指定目录；未指定时使用当前工作目录。
2. 只检查项目根目录是否存在 `.mcp.json`，不读取其中的凭据。若不存在，从随 Skill 分发的 [MCP 配置模板](assets/mcp.example.json) 复制一份到项目根目录并命名为 `.mcp.json`；不得覆盖已有文件。
3. 创建配置后读取 [MCP 配置引导](references/mcp-setup.md)，让用户选择“仅官方（推荐）”“仅社区”或“两者都配置”，按选择给出对应操作。不得要求用户在对话中提供 Token。随后停止，等待用户完成本地配置并重启 Claude。
4. 已有 `.mcp.json` 时不修改它，继续从 URL 解析具体 `node-id`，保留用户指定的节点范围；不扩大到整个 Figma 文件。
5. 只做有界识别：读取项目说明和入口配置，确认它是现有 Web 前端项目。无法确认就停止。
6. 记录本次任务的目标页面或组件、用户明确的响应式与交互要求，以及禁止修改的范围。

## 2. Provider

按以下顺序选择，并在读取设计前向用户说明选中了哪个 Provider：

```text
用户显式指定 → 官方 Figma MCP → Figma-Context-MCP → 停止
```

- 可用性只由当前会话中完成所需操作的真实可调用工具判断，不由 Server 名称、配置文件或已保存凭据判断。
- 两者都可用且用户未指定时，选择官方 Figma MCP。
- 仅官方 Provider 可用时使用官方；仅 Context Provider 可用时使用 Figma-Context-MCP；两者都不可用时说明缺失工具并停止。
- 用户指定的 Provider 不可用时，读取 [MCP 配置引导](references/mcp-setup.md)，给出该 Provider 的本地配置或认证步骤，然后停止；不静默切换。
- 选择后只使用该 Provider。失败时按对应 Reference 分类；临时超时、可恢复限流或资源下载失败最多安全重试一次，明确返回席位或周期额度耗尽时不重试。
- 用户未显式指定 Provider、默认官方 Provider 返回 OAuth 未授权、授权被拒绝或授权过期，且 Context Provider 的必需操作可调用时：先说明授权失败和即将切换，再丢弃官方调用的任何结果，从目标 `node-id` 开始用 Figma-Context-MCP 重新读取。Context Provider 不可用时停止。
- 用户显式指定官方 Provider 时，即使返回上述三类 OAuth 授权状态也停止，不自动切换。其他 OAuth 故障、官方服务异常、限流、超时、权限不足、节点错误、数据为空或不完整、以及后续还原偏差均不得触发切换。
- 不安装或认证工具；除创建缺失的无凭据模板外，不修改 MCP 配置，也不处理 OAuth、Token 或环境变量值。
- 用户完成配置并重启后，必须按 [MCP 配置引导](references/mcp-setup.md) 用当前会话中的实际可调用工具验证所选 Provider；不能仅根据 `.mcp.json` 判断成功。

按选中的 Provider 读取一个 Reference：

- [官方 Figma MCP](references/provider-official.md)
- [Figma-Context-MCP](references/provider-context-mcp.md)

## 3. Design context

写代码前必须取得目标节点的结构化布局与样式信息，并按需取得截图和真实资源。

- 大节点先读结构，再按主要子节点拆分；所有读取都保持在已确认的 `node-id` 范围内。
- 截图用于视觉参照，不能替代结构化信息。
- 响应式和交互意图的依据顺序是：用户明确说明 → Figma 注释、Variants、Constraints → 项目已有模式 → 询问用户。
- Figma 的参考代码或组件提示只是设计证据，不能直接当作目标项目代码。
- 缺少结构化内容、目标节点不匹配或范围不明确时停止。

## 4. Project rules

从目标项目目录向上查找 `D2C.md`，到当前 Git 仓库根为止；无 Git 仓库时只检查目标项目目录。只采用适用于目标项目的规则；多个文件按父级到子级读取，同项以就近规则为准，适用范围不明确时询问用户。

已有 `D2C.md` 时：

- 读取它作为稳定项目规则，但仍现场核对任务相关代码。
- 当它与当前代码冲突时，以当前代码为事实，在实现预览中列出冲突；不得自动更新 `D2C.md`。

未找到适用的 `D2C.md` 时：

1. 按[项目分析指南](references/project-analysis-guide.md)对稳定项目规则做有界取证。
2. 以[D2C.md 模板](templates/D2C.md)在对话中展示候选内容；只写有证据的稳定规则，对无法确认的组织规则询问用户。
3. 等待用户明确确认。确认前不创建文件，不进入业务实现。
4. 确认后把内容写入项目根目录 `D2C.md`，再继续当前任务。

这是首次使用的第一次确认。后面的实现预览仍需要单独确认。页面细节、临时兼容、API、路由、权限和埋点不写入 `D2C.md`。

## 5. Project analysis

按[项目分析指南](references/project-analysis-guide.md)检查本任务相关的代码和资源。范围限于项目说明与配置、组件/主题/样式入口、一个或两个相似页面，以及当前任务涉及的路由、数据和验证命令；不得全库漫游。

分析必须回答：

- 候选组件属于三方组件、项目封装公共组件还是页面局部组件；公共组件有哪些调用方和影响。
- 设计值能否映射到现有 Token/变量/主题，能否复用样式工具（Mixin、函数、utility class），其作用范围和额外影响是什么。
- 字体、图片和图标是否已有真实资源；缺失项和可选处理是什么。
- 现有业务逻辑、数据来源、交互、路由、权限和可访问性要求哪些必须保留，哪些仍未知。
- 实际可用的 changed-surface 验证命令和真实页面入口是什么。

## 6. Implementation preview

在对话中展示实现预览，不创建独立预览工程。用户明确的定位、响应式和交互要求必须在对应图示或方案中体现，未确定项明确列出。预览必须包含：

1. 基于实际项目布局的带指标 ASCII 图。主要容器分别标明宽高是固定、随内容撑开、填满可用空间还是受最小/最大值约束，并标注关键尺寸、padding、gap 和对齐。复杂节点先给总览，再按独立布局组件拆分子图；不按 Figma 图层机械拆分，名称保持一致。
2. 组件子图把关键样式标在对应元素附近：文字的字号、行高、字重和解析后颜色，容器的背景、圆角、边框和阴影，以及图片、图标尺寸和当前状态。重复样式只标一次；缺失项写“待核对”，不得猜测。
3. 补充图中不宜承载的响应式变化、复杂渐变、复杂阴影和多状态；区分 Figma 明确值、布局计算结果和项目规则调整值，不重复图中内容。
4. 组件计划：逐项标明三方、项目封装公共或页面局部；公共组件列出调用方和影响。
5. Token 映射：Figma 值、项目现值、候选映射、匹配依据、修改方案和作用范围。
6. 资源与字体状态：真实资源位置、缺失或下载失败，以及需用户选择的替代方式。
7. 数据与交互：现有来源、准备保留的业务行为、缺失接口和未明确行为。
8. 预计新增或修改的文件、组件和样式范围。
9. Figma 与项目语义标签、表单标签、键盘、焦点、禁用态或错误提示之间的可访问性冲突。
10. 尚不能确定的内容和需要用户决定的选项。

空信息不建表；只有冲突项展开对比。预览最后明确询问用户是否按此方案写入。得到明确确认前，不写任何业务代码。

Figma 原始值与项目已有强约束冲突时，默认遵守项目约束，并在预览中列出 Figma 原值、项目规则、拟采用值和可见差异；用户要求例外时，按下述调整流程重新确认。项目特有规则只保存在具体项目的 `D2C.md`，不写入通用 Skill。

用户调整时，执行并显示这条链路：

```text
re-read affected Figma evidence + re-read affected project evidence
→ compare against latest request
→ latest request wins over Figma
→ explain business/project/safety conflicts
→ recompute component and Token impact
→ show changed preview and wait again
```

用户最新要求与 Figma 冲突时，以最新要求为准；与现有业务逻辑、项目强约束或安全要求冲突时，先解释影响并等待决定。不得沿用已经失效的组件或 Token 影响判断。

## 7. Confirmed write

只在已确认的文件与影响范围内写入，主模型负责全部文件修改和高影响决策。

- 三方组件：不改依赖源码；只用公开属性、主题能力、作用域样式或项目包装。仍无法满足时交给用户决定。
- 项目封装公共组件：预览其调用方和影响并取得明确确认；优先增加向后兼容属性，不改变默认行为。
- 页面局部组件：可在确认范围内修改。
- Token：匹配时复用现有值；不匹配时展示来源、现值、设计值、候选方案和作用范围。单页还原优先局部适配，不自动修改全局或公共 Token；无可靠映射时可在页面内保留 Figma 原始值。
- 资源：使用 Figma 真实资源并放入项目既有资源目录；不用占位图，不从截图手绘未知 SVG，不让临时下载地址进入长期代码，不为一个图标随意增加图标库。
- 数据：保留现有业务逻辑，不从视觉稿猜 API、Store、权限、埋点或路由。新页面没有数据合同时，只可用页面局部静态示例数据呈现可见状态并标明“业务数据待接入”；用户不接受时等待真实结构。
- 可访问性：保留语义标签、表单标签、键盘操作、焦点、禁用态和错误提示；只承诺检查本次改动表面，不声称完成全面审计。

## 8. Engineering validation

验证命令来源顺序：

```text
D2C.md → package scripts、路由和项目说明 → 询问用户
```

- 按 changed surface 执行适用的类型检查、Lint、测试和构建，并记录实际命令与结果。
- 确认由本次修改引起的错误后修复并重试一次；不得自动进入更多修复循环。
- 历史错误、环境错误、未执行和跳过的检查分别报告。
- 不改无关代码，不关闭规则，不降低类型约束来制造通过结果；跳过的检查不能写成已完成。

## 9. Visual review

按[视觉复核指南](references/visual-review.md)在目标项目真实路由进行复核。根据当前会话能否直接查看两张截图分流：不能时用 Chrome 做 Figma 与 DOM/计算样式的结构化对比；能查看时仅在发现具体偏差后用 Chrome 定位。DOM 数值不能代替视觉判断，最多进行一次源码修正和一次复查。

## Subagent 边界

Subagent 是可选的只读助手，不是固定阶段。仅可把一个问题或一个受限目录交给它：

- 查找可复用组件及调用方。
- 分析 Token、主题和样式的影响范围。
- 查找任务相关路由、数据来源和验证命令。
- 已确定具体视觉偏差后，收集目标区域的 Chrome 证据。

每个 Subagent 只返回证据文件、候选方案、影响、冲突和未知项；不得写文件，也不得接触凭据。主模型必须复查高影响结论，并始终负责 Provider/认证状态判断、`D2C.md` 整理与确认、整体实现预览、公共组件/Token/业务边界、所有写入、视觉结论和最终交付。无 Subagent 能力时由主模型按同一清单串行完成。

## 10. Delivery

最终交付必须包含：

- 使用的 Provider、Figma 节点范围和目标项目/真实路由。
- 新增与修改文件清单。
- 组件复用、公共组件影响、Token 映射及最终作用范围。
- 资源、字体、数据、交互和可访问性处理，以及仍存在的缺口。
- 工程验证的实际命令、结果、一次修复/重试；历史或环境错误与未执行项分开列出。
- 视觉复核所用的 Figma Frame 视口、真实页面证据、一次修正和一次复查结果。
- 已知差异、未知项、需要用户人工验收的内容，以及页面无法打开时的明确“未验证”边界。

没有结构化设计上下文、没有完成必要确认、没有完成代码写入或无法打开真实页面时，不把部分结果描述为完整交付。
