# 可选 Debug 记录

仅在用户明确开启 Debug 时读取。本模式沿用日常 D2C 流程，由主模型直接维护一个 Markdown 文件，不增加执行脚本。

## 文件与时机

- 确认目标项目目录存在且范围明确后，在该目录创建或覆盖 `d2c-debug.md`（不是上级共享 `D2C.md` 所在目录）。每个开启 Debug 的新任务只保留最新一次；同一任务后续阶段更新该文件，不反复清空。
- 开头记录任务、日期、Figma URL/节点、当前 Provider、记录起点和当前进度。尚未取得的信息写“未取得”。
- 在关键结果、用户调整、错误或停止点及时更新对应章节，保留同一任务内影响结果的变更原因；不等最终交付才一次性生成。意外中断只能保留最后成功写入的内容。
- 中途开启时，只用当前可追溯证据补充此前内容，注明记录起点和缺失部分，不推测历史。用户关闭后停止更新。
- 写入失败时提示文件未完整保存及原因，继续按原流程处理任务；调试失败不阻断 D2C，也不绕过原有停止条件。交付或停止时说明记录完整性并链接已保存文件。

## 四类内容

| 类别 | 最小记录内容 |
| --- | --- |
| 设计证据 | Provider、节点；影响实现的关键布局/样式值及来源；缺失信息 |
| 项目适配 | 候选组件、Token、样式工具及代码位置；核对后的值或行为；最终选择与依据 |
| 实现取舍 | 设计或用户要求 → 最终实现；差异原因、影响及确认情况；用户调整及受影响决策 |
| 验证结果 | 实际命令或检查方式、范围与视口；预期值和实际表现；差异、修正结果和未验证项 |

只展开影响结果的关键项，正常匹配和重复内容合并；每项尽量用一行或短段落。引用节点、项目相对代码路径或已有截图，不复制完整设计数据、源码、工具输出或内部思考过程。不读取或记录认证凭据，错误信息与链接中的凭据也需省略。

已证实原因与推测分开，证据不足写“原因未确认”；结构化匹配不等于视觉一致。文件仅供查看分析，不作为恢复执行、缓存或状态管理依据，不增加自动评分或修复循环。
