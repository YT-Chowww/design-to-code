# D2C Skill 需求草案 V2

> 状态：需求与方案已确认
> 更新时间：2026-09-09
> 本文记录本轮已经确认的需求结论，不包含具体实现方案。

## 1. 项目定位

D2C 是一个面向现有前端项目的轻量 Skill。它读取指定 Figma 节点的设计上下文，并将设计实现为符合目标项目约定、可以运行和验证的代码。

主 Skill 面向 Web 前端，流程本身不写死具体框架。首版实际验证范围为 React + TypeScript 和 Vue 3 + TypeScript；具体组件库及项目规则放入对应 Reference。

核心价值是：

- 理解目标项目的技术栈和既有代码。
- 复用已有组件、Token、样式和业务模式。
- 将 Figma 的参考实现转换成项目实际使用的代码。
- 保留设计范围之外的既有业务逻辑。
- 使用真实图片、图标和其他设计资源。
- 执行项目适用的工程检查和视觉复核。

本项目不重新实现 Figma 数据服务，也不建设通用代码生成或任务编排平台。

本次实现以轻量化为优先：仅保留完成 D2C 所必需的流程，不为了诊断、审计或自动恢复增加常驻执行内核和中间产物体系。

## 2. MCP 与 Skill 的边界

整体职责分为三层：

    Figma MCP Provider
    → 通用 D2C Skill
    → 目标项目自己的 D2C.md

### Figma MCP Provider

负责提供设计数据和资源，不负责最终业务代码实现。

支持：

- Figma 官方 MCP。
- Figma-Context-MCP。

### 通用 D2C Skill

负责：

- 执行前检查所需 Figma MCP 工具当前是否可用。
- 选择并提示本轮使用的 Provider。
- 获取和理解设计上下文。
- 分析目标项目。
- 按项目约定实现代码。
- 执行工程验证和视觉复核。
- 在错误或关键歧义出现时交给用户判断。

### 项目 D2C.md

负责保存当前项目已经确认的稳定规则，例如：

- 技术栈、组件库和工程约定。
- Token、主题、字体和资源规则。
- 布局、响应式、数据和交互边界。
- 代码修改边界及验证方式。

## 3. Provider 规则

Provider 选择顺序：

    用户显式指定
    → Figma 官方 MCP
    → Figma-Context-MCP
    → 停止

已确认规则：

- 两种 Provider 都可用时，默认使用官方 MCP。
- 获取设计前必须明确提示本轮使用的 Provider。
- Provider 识别以当前可调用工具为准，不依赖 Server 名称。
- 用户显式指定的 Provider 不可用时停止，不自动切换。
- 未显式指定 Provider 时，默认官方返回 OAuth 未授权、授权被拒绝或授权已过期，且社区 Provider 可用时，提示后丢弃官方结果并从目标节点改用社区 Provider。
- 显式指定官方时上述三类授权状态仍停止；其他 OAuth 故障、服务异常、限流、超时、权限或节点错误、设计数据不完整和还原偏差都不触发切换。
- 不混用两个 Provider 的不完整结果。

认证由用户提前完成：

- 官方 MCP 使用用户自己的 OAuth。
- Figma-Context-MCP 使用用户配置的 Token。
- Skill 不负责安装、启动或认证 MCP；仅在目标项目缺少 `.mcp.json` 时，从随 Skill 分发的无凭据模板创建该文件，提示用户在本地完成配置并重启 Claude 后停止。
- 配置引导提供“仅官方（推荐）”“仅社区”“两者都配置”三种模式，并在重启后以实际可调用工具验证所选 Provider，不以配置文本推断成功。
- Skill 不覆盖已有 `.mcp.json`。允许检查配置是否存在、Provider 是否配置及认证状态；不得读取、输出或保存 OAuth、Token、环境变量等凭据值。

可用性检查规则：

- 以当前是否存在且能够调用所需工具为判断依据，不根据 MCP Server 名称或配置文件判断是否安装。
- 所需工具不存在时，提示用户安装或启用对应 MCP。
- 工具存在但认证失败时按 Provider 规则处理，不检查凭据值。
- Skill 只负责发现和说明问题，不执行安装、登录或配置修改。

## 4. 输入范围

必需输入：

- 包含具体 `node-id` 的 Figma URL。
- 当前工作目录或用户明确指定的目标项目目录。

可选输入：

- 新增或修改已有页面。
- 指定目标文件或模块。
- 指定使用的组件库。
- 是否包含交互、响应式或动效。
- 指定使用的 MCP Provider。

明确不支持 Figma Desktop 当前选中节点。没有 `node-id` 时停止，不读取整个文件或猜测目标 Frame。

## 5. 设计上下文

写代码前必须先成功读取指定节点的设计上下文。它通常包含布局、样式、组件提示和截图。图片、图标等资源可以在实现过程中按需获取。

官方 MCP 的参考代码只作为设计表达，必须转换成目标项目的实际框架、组件和样式写法。

Figma-Context-MCP 提供结构化布局和样式数据时，不要求额外转换并保存统一的 normalized JSON。

设计上下文过大或读取失败时，可以先获取节点结构，再按主要子节点拆分读取。始终无法取得结构化内容时停止，不能仅凭截图猜测实现。

响应式和交互意图按以下顺序判断：

    用户明确说明
    → Figma 注释、Variants 和 Constraints
    → 项目现有模式
    → 无法确定时提出问题

该顺序用于理解设计意图和新增行为。已有页面的业务逻辑仍应保留，不能仅凭 Figma 覆盖；无法确定的断点、状态、校验或点击行为必须在实现预览中说明，不自行猜测。

## 6. 目标项目分析

稳定的项目知识通过已有说明文件和 Reference 复用，不建立自动生成、自动失效的项目扫描缓存。

信息来源按以下范围划分：

- 通用 D2C 规则保存在主 Skill。
- 项目已经确认的稳定规则保存在项目自己的 `D2C.md`。
- 项目约定优先读取已有的 `AGENTS.md`、`CLAUDE.md` 等说明文件。
- 每次只现场检查与当前任务有关的目标文件、相邻实现和工作区状态。
- 路由、状态管理、接口和其他工程模式仅在当前设计涉及时检查。
- Reference 与实际代码冲突时，以当前代码为准。

## 7. 实现预览与用户确认

成功读取 Figma 设计上下文并分析目标项目后，必须先在对话中向用户展示实现预览，再修改代码。

实现预览包含：

- 一张结合目标项目现有布局的 ASCII 结构图。
- 核心布局方式、宽高和间距。
- 字体、颜色、圆角等关键样式。
- 计划复用、修改或新增的组件，并标明属于三方库、项目封装还是页面局部组件。
- 关键 Figma 值与项目 Token、变量或主题配置的映射方式及影响范围。
- 字体、图片和图标的可用性，以及必要的替代方案。
- 页面数据来源，以及尚未提供的接口或业务行为。
- 预计修改的页面、组件或样式范围。
- 视觉稿与项目现有可访问性规则之间的冲突。
- 当前无法确定的内容。

ASCII 图用于校对结构理解，不代替最终视觉验证。预览不写入中间文件或报告。Skill 展示后必须暂停，只有用户确认或提出调整后才能修改代码。

用户提出调整时：

- 重新检查受影响的 Figma 节点、截图和目标项目代码。
- 将用户最新要求与 Figma 原始信息进行比较；两者冲突时以用户最新要求为准。
- 用户要求与既有业务逻辑、项目强约束或安全要求冲突时，说明影响并等待用户决定。
- 根据新要求重新判断组件复用、Token 映射和影响范围，更新实现预览后再次等待确认。

## 8. 项目代码适配

实现时要求：

- 优先复用已有组件和 Token。
- 三方库组件不得直接修改依赖源码，优先使用公开属性、主题能力、样式覆盖或项目侧包装；仍无法满足时交给用户决定。
- 修改项目封装的公共组件前，必须在实现预览中列出影响范围并等待用户确认；实现时优先采用新增属性等向后兼容方式，不改变原有默认行为。
- 页面局部组件可以在用户已确认的任务范围内修改。
- Code Connect 信息存在时优先采用。
- 没有可靠 Token 时允许保留 Figma 原始值。
- 修改已有页面时保留设计范围外的业务逻辑。
- 不根据视觉稿猜测 API、权限、埋点或路由行为。
- 新页面没有现成接口或业务逻辑时，默认使用页面范围内的静态示例数据还原 Figma 中可见的状态，并明确标记业务数据待接入。
- 不为示例数据创建虚假 API、Store、权限或路由逻辑；用户不接受示例数据时，在实现预览阶段停止并等待真实数据结构。
- 不引入无关依赖或与项目不一致的样式方案。
- 保留用户已有工作区改动。
- 保留项目已有的语义标签、表单标签、键盘交互、焦点、禁用态和错误提示方式，不为视觉还原静默破坏可用性。

Token、变量和主题配置规则：

- 覆盖 CSS Variables、Less/Sass 变量、JavaScript/TypeScript 主题对象、组件库 Token、Tailwind theme 及项目自定义设计变量。
- 按三方库主题、项目全局主题、公共组件级、页面或局部组件级识别作用范围，不按具体语法做固定判断。
- Figma 值与现有值一致时，优先复用项目已有 Token 或变量。
- 两者不一致时，在实现预览中展示来源、当前值、Figma 值、候选映射和影响范围，由用户确认取舍。
- 不为还原单个页面自动修改三方库主题、项目全局主题或公共组件级变量，优先使用组件级或页面级适配。
- 找不到可靠映射时，允许在当前页面或局部组件中保留 Figma 原始值。

## 9. 资源要求

- 分析阶段检查 Figma 字体、图片和图标能否在目标项目中使用。
- 使用 Figma 提供或导出的真实图片和图标。
- 不使用占位资源。
- 不根据截图手绘未知 SVG。
- 不为单个图标随意引入新的图标库。
- 临时资源地址不能直接作为长期提交内容。
- 需要进入仓库的静态资源应保存到目标项目已有资源目录。
- 字体缺失、资源下载失败或只能取得临时地址时，必须在实现预览中说明，不静默替换。
- 项目存在可靠的等价资源时可以提出复用方案；否则由用户决定替代方式或接受差异。

## 10. 验证与交付

生成后使用目标项目已有命令，执行与本次改动相关的类型检查、Lint、测试或构建。本次代码引起的明确错误由模型修复后重试一次；项目历史错误、环境问题或无法判断的错误，说明情况并交给用户决定。

验证时需要区分：

- 本次改动引入的问题。
- 项目已有问题。
- 环境或依赖问题。
- 尚未执行的检查。

视觉复核检查目标项目中的真实页面，并对照 Figma 检查布局、尺寸、文字、颜色、资源、交互状态和响应式行为。视觉偏差必须先由支持多模态的模型或用户发现，Chrome MCP 只在确认存在偏差后辅助定位，不作为每次验证的必经步骤。

按当前会话能力分流：

- 当前模型能够读取图片时，由模型先对照 Figma 与真实页面截图；没有发现明显偏差时结束视觉复核。
- 当前模型不能读取图片时，向用户提供 Figma 参考和真实页面入口，等待用户判断，不能用 DOM 数值代替视觉结论。
- 用户指出偏差后再使用 Chrome MCP 检查相关元素；反馈过于笼统时，先询问具体区域或问题类型。
- Chrome MCP 检查应聚焦相关元素的尺寸、盒模型、计算样式和父级布局，并追溯到项目源码。
- DevTools 中的临时样式修改只用于定位和试验，最终必须修改项目源码。
- 修正后复核一次；剩余差异交给用户判断，不循环修正。
- 不按模型名称维护多模态能力白名单，以当前会话实际能否读取图片为准。

真实页面验证规则：

- 优先从项目脚本、路由和现有说明中确定启动命令与访问地址。
- 按 Figma Frame 尺寸设置验证视口。
- 无法确定页面入口时询问用户。
- 登录、权限或数据环境阻塞时明确说明，不为截图修改路由、绕过登录或注入临时业务 Stub。
- 检查本次改动涉及的基础语义、表单标签、键盘交互和状态反馈，但不承诺完整 WCAG 审计。
- 已确认存在视觉偏差但 Chrome MCP 不可用时，提供页面入口和人工检查提示，不宣称完成元素级定位。

无法运行或无法截图时必须明确说明，不能宣称已经完成视觉验证。

不生成独立验证报告、评分或状态文件。最终回复说明修改文件、复用内容、工程验证结果、视觉复核结果、已知差异和人工验收边界。

## 11. 错误与重试

- 临时超时、限流或资源下载失败最多安全重试一次。
- OAuth、Token、设计范围、业务行为和视觉取舍问题交给用户决定。
- Provider 切换仅允许上述默认官方 OAuth 失败分支，并且必须先提示、从头读取且不混用结果。
- 不建设跨会话状态机、自动恢复引擎或自动多轮视觉收敛。

## 12. 项目 Reference

主 Skill 保持通用，不内置 E-Space PC、E-Space 移动端或其他项目的预设规则。每个目标项目独立生成并维护自己的 `D2C.md`。

主 Skill 只提供：

- 通用的项目分析清单，用于指导模型检查技术栈、组件、Token、布局、资源、数据和验证方式。
- 通用的 `D2C.md` 内容骨架，不预填具体框架、组件库或组织规则。

内容骨架包含：

- 技术栈。
- 组件使用。
- Token 与主题。
- 布局与响应式。
- 字体与资源。
- 数据和交互。
- 代码修改边界。
- 启动与验证。

首次执行规则：

- 项目不存在 `D2C.md` 时，根据分析清单检查实际代码。
- 先在对话中展示拟写入的项目规则，并要求用户补充无法从代码确认的内容。
- 用户确认后生成项目根目录的 `D2C.md`，再用于当前及后续 D2C 执行。

后续执行规则：

- 优先读取项目已有的 `D2C.md`。
- `D2C.md` 由项目团队提交、评审和维护，不由主 Skill 集中更新。
- `D2C.md` 与当前代码冲突时，以实际代码为准，并在实现预览中提示。
- 具体页面实现、临时兼容逻辑、业务接口、路由、权限和埋点规则不写入 `D2C.md`。

## 13. Subagent 使用边界

Subagent 是复杂任务中的可选只读分析助手，不作为固定执行阶段。小型任务由主模型直接完成。

适合并行分析的范围包括：

- 可复用组件及其调用方。
- Token、主题和样式影响范围。
- 路由、数据来源和验证入口。
- 已确认视觉偏差后的局部 Chrome 证据。

每个 Subagent 只处理一个明确问题或受限目录，返回证据、候选方案、影响、冲突和未知项。首版不允许 Subagent 修改代码，也不向其传递凭据。

Provider 与认证判断、`D2C.md` 最终内容、整体实现预览、组件和 Token 决策、文件写入、视觉结论与最终交付均由主模型负责。高影响结论必须由主模型复查。不支持 Subagent 的环境由主模型按相同清单完成。

## 14. Benchmark 需求

Benchmark 作为独立 `d2c-benchmark` Skill，不进入日常 `d2c` 主流程。

### 固定场景

使用一个专用、内容稳定的 Figma 基准文件，包含 4 个节点：

- PC 数据管理页。
- PC 图表分析页。
- 移动端内容展示页。
- 移动端表单交互页。

### 固定脚手架

- PC：React + TypeScript + Ant Design。
- 移动端：Vue 3 + TypeScript + Vant。
- 图表使用脚手架预装的统一图表库。
- 使用本地模拟数据，不接真实后端。
- 模型不能自行更换或新增基础组件库、图表库。

### 执行方式

- 使用用户当前本地配置的模型。
- 一次执行全部 4 个场景。
- 每个场景从相同的干净脚手架基线开始。
- 各场景结果相互隔离。
- 除实现预览确认外，复用日常 `d2c` 的设计读取、生成适配和验证规则，不提供额外生成提示。
- Benchmark 在隔离脚手架中执行，不修改业务项目，因此不逐场展示实现预览或等待确认；全部场景运行后由用户在统一入口查看结果。
- Provider 规则与主 `d2c` 保持一致。
- 单个场景失败时继续执行其他场景。
- MCP 或脚手架整体不可用时停止全部测试。
- 每次只保留最新一次结果。

### 预览方式

提供一个统一预览入口，使用 4 个标签页展示场景。

每个场景：

- 左侧显示 Figma 原始设计。
- 右侧嵌入真实、可交互的生成页面。
- 页面宽度与对应 Figma Frame 保持一致。
- 长页面允许纵向滚动。
- 移动端按设计稿设备宽度展示。
- 失败场景展示失败原因。

Benchmark 不提供评分、通过判断、模型排名或能力等级，用户直接根据预览结果判断效果。

## 15. 首版不包含

当前不考虑：

- Figma Desktop 当前选择。
- 自建 Figma MCP。
- 通用代码生成引擎。
- `.d2c` 运行工作区。
- 独立 Preview 工程作为日常流程。
- manifest、normalized design 和阶段报告。
- 跨会话恢复，以及上述三类 OAuth 授权状态以外的自动 Provider 降级。
