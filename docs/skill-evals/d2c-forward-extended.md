## 6. Official-only Provider

精确 prompt 后缀：

```text
场景：只有官方 Figma MCP 可调用，用户未指定 Provider，URL 含具体 node-id。请给出实际用户响应、下一步动作和停止点；明确 Provider 选择以及写入边界。只用给定事实。
```

预期决策：说明并使用官方 Figma MCP；不把 Context MCP 说成已选或必需；遵守写入前的停止点。

原始输出：

> 流程：preflight → provider → design context → project rules → project analysis → implementation preview → confirmed write → engineering validation → visual review → delivery。
>
> 已从 URL 确认具体 `node-id`。你未指定 Provider，当前仅官方 Figma MCP 可调用，因此本次将使用**官方 Figma MCP**；不会尝试或切换到 Figma-Context-MCP，也不会处理任何认证或凭据。
>
> 下一步我会在当前项目目录做有界识别，确认它是现有 Web 前端项目；随后仅读取该节点范围内的结构化布局、样式信息，并按官方 Provider 的规则取得所需设计证据。接着检查项目根目录是否已有 `D2C.md`，并分析相关组件、Token、主题、相似页面和验证命令。
>
> 停止点与写入边界：
>
> - 若当前目录不能识别为现有 Web 前端项目，立即停止，不写文件。
> - 若无法取得该节点的结构化设计上下文，立即停止，不用截图猜测实现。
> - 若缺少 `D2C.md`，我只会先在对话中展示候选内容；未获确认前，不创建 `D2C.md`，也不进入业务实现。
> - 完成项目分析后，我会展示 ASCII 结构图、布局与样式、组件/Token 影响和拟改文件；未获第二次明确确认前，不修改任何业务代码。

映射结论：PASS。输出明确选择官方 Provider，并逐项给出项目、结构化上下文和两次确认的停止点。

## 7. Context-only Provider

精确 prompt 后缀：

```text
场景：只有 Figma-Context-MCP 可调用，用户未指定 Provider，URL 含具体 node-id。请给出实际用户响应、下一步动作和停止点；明确 Provider 选择以及写入边界。只用给定事实。
```

预期决策：说明并使用 Figma-Context-MCP；不因官方 MCP 缺失而停止；遵守写入前的停止点。

原始输出：

> 已选择 **Figma-Context-MCP**：当前未指定 Provider，且只有它能调用。我会仅用该 Provider 在你指定的 `node-id` 范围内读取结构化设计信息；不会读取或处理 Token/OAuth，也不会自动改用其他 Provider。
>
> 下一步会先在当前工作目录做有界项目识别，确认存在可落地的 Web 前端项目；确认后读取该节点的结构化布局、样式和所需资源，再分析项目组件与 Token，并先给你实现预览。
>
> **下一步动作**
>
> 1. 解析并锁定 URL 内的具体 `node-id`。
> 2. 有界读取当前项目的说明与入口配置，确认它是现有 Web 前端项目。
> 3. 使用 Figma-Context-MCP 读取该节点的结构化设计上下文。
>
> **停止点**
>
> - 当前目录无法确认是现有 Web 前端项目时，停止，不读取设计、不写文件。
> - 无法取得该节点的结构化设计信息时，停止，不以截图猜测实现。
> - 即使后续已取得信息，也必须先完成 `D2C.md`（首次项目）和实现预览两次确认，才可能写入业务代码。

映射结论：PASS。输出明确选择 Context Provider，并在官方缺失时继续正确流程。

## 10. User adjustment conflicts with Figma

精确 prompt 后缀：

```text

```

预期决策：重新读取受影响的 Figma 与项目证据；以用户最新要求为准；重算影响并再次确认，确认前不写入。

原始输出：

> 我会先重新读取受影响的 Figma 节点结构与样式证据，并重新核对涉及的项目布局、组件调用方及 Token 作用范围；然后将它们与您刚提出的布局调整逐项比较。
>
> 以您的最新要求为准，不再把冲突的 Figma 布局当作实现目标。若调整会影响现有业务逻辑、项目强约束或安全要求，我会先说明影响并等待您的决定。
>
> 本次会重新计算：
>
> - 受影响的页面局部组件、公共组件调用方，以及是否需要新增兼容属性；
> - 原 Token 映射是否仍成立，哪些改为页面局部样式，哪些会触及公共或全局范围；
> - 布局、响应式、交互和可访问性影响；
> - 原实现预览中失效的部分与对应文件改动范围。
>
> 随后我会展示更新后的 ASCII 结构图、核心布局和样式、组件与 Token 影响、冲突及待确认项，并再次请您确认是否按新方案写入。
>
> 在您确认更新后的实现预览前，**不会写入任何业务代码或样式文件**。

映射结论：PASS。输出完整覆盖重新读取、优先级、影响重算、更新预览和再次确认。

> 3. 若失败，停止在资源处理阶段，等待你选择“稍后重试”或“明确切换 Provider”。

## 12. Known mismatch with Chrome unavailable

精确 prompt 后缀：

```text
场景：多模态比较或用户已指出一个具体布局偏差，但 Chrome 检查工具不可用。请给出实际用户响应、能做与不能做的检查、偏差记录和停止点；明确是否猜测 DOM 数值、声称修复成功或写入文件。只用给定事实。
```

预期决策：记录已知偏差和 Chrome 不可用边界；不猜 DOM、不声称修复、不写入，保持未验证状态。

原始输出：

> 给用户的实际响应：
>
> 已记录到具体偏差，但当前会话没有可用的 Chrome 检查工具，无法取得该区域的元素尺寸、盒模型、计算样式、父级布局、资源加载或对应源码证据。
>
> 我不会据此猜测 DOM 数值，也不会凭推测修改源码或声称已经修复成功。当前先将该偏差保留为待复核项；请在具备 Chrome 检查能力的会话中，对该具体区域进行定点检查后再决定是否修正。
>
> 能做的检查：
>
> - 若模型具备多模态能力：基于已提供的 Figma 参考与真实页面截图，确认并描述用户已指出的具体视觉差异。
> - 若不具备多模态能力：仅记录用户指出的区域、实际表现与期望表现；不自行得出视觉结论。
> - 均可记录该偏差为“等待 Chrome 定点证据”的未验证项。
>
> 不能做的检查：
>
> - 不能用 Chrome 获取目标区域的尺寸、盒模型、计算样式、父级布局、资源加载或源码定位。
> - 不能以 DOM 数值替代视觉判断。
> - 不能验证修正原因，更不能完成修正后的真实页面复查。
>
> 偏差记录：
>
> - 状态：`待 Chrome 定点证据`
> - 范围：用户指出的具体布局区域
> - 原因：Chrome 检查工具当前不可用
> - 结论：真实页面视觉复核未完整验证
>
> 停止点：在取得 Chrome 定点证据或用户另行决定前停止；不写入任何文件、不修改源码、不声称视觉一致或修复完成。

映射结论：PASS。输出明确列出可做/不可做检查，并将结果保持为未验证。
