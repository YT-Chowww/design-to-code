# 轻量 D2C Skill 方案设计

> 日期：2026-09-09
> 状态：已确认
> 需求基线：`docs/d2c-skill-requirements-v2.md`

## 1. 设计结论

采用一个轻量、通用的日常 `d2c` Skill，加一个独立的 `d2c-benchmark` Skill。

日常 `d2c` 只负责编排模型如何读取 Figma、理解当前项目、向用户预览实现思路、修改代码并验证结果。它不引入 TypeScript 执行内核、状态机、标准化设计文件、自动恢复或阶段报告。错误由模型说明，用户决定是否调整或重试。

项目长期规则不放进 Skill，也不提供 E-Space 等项目模板。每个项目在根目录维护自己的 `D2C.md`。Skill 只提供通用分析清单和空白内容骨架。

`d2c-benchmark` 使用固定 Figma 节点和隔离脚手架，一次生成四类真实页面，供用户并排查看原稿与结果。它不评分、不判定通过，也不代表日常项目合入能力。

## 2. 目标与边界

### 2.1 目标

- 将包含明确 `node-id` 的 Figma 设计实现到现有 Web 前端项目。
- 优先复用项目组件、Token、主题、资源及业务模式。
- 修改代码前，通过 ASCII 图和核心实现说明让用户校正理解偏差。
- 在真实页面中进行工程验证和视觉复核。
- 同时支持 Figma 官方 MCP 与 Figma-Context-MCP。
- 首版实际验收 React + TypeScript 与 Vue 3 + TypeScript 项目。

### 2.2 不承担的职责

- 不安装、启动、认证或配置 MCP。
- 不读取、保存、复制或输出 OAuth、Token 等凭据。
- 不建设通用代码生成引擎、任务平台或多用户账号平台。
- 不支持 Figma Desktop 当前选择。
- 不创建 `.d2c` 工作区、manifest、normalized JSON 或阶段报告。
- 不提供跨会话恢复、OAuth 未授权、授权被拒绝或授权已过期以外的自动 Provider 降级，也不提供自动多轮视觉收敛。
- 不在日常流程中创建独立预览工程。
- 不自动评分、排名或判断模型是否可用。

## 3. 总体结构

```text
d2c/
├── SKILL.md
├── references/
│   ├── provider-official.md
│   ├── provider-context-mcp.md
│   ├── project-analysis-guide.md
│   └── visual-review.md
└── templates/
    └── D2C.md

d2c-benchmark/
├── SKILL.md
├── references/
│   └── scenarios.md
├── templates/
│   ├── pc-react-antd/
│   └── mobile-vue-vant/
└── scripts/
    └── deterministic scaffold reset/preview helpers
```

### 3.1 拆分原则

- `SKILL.md` 保存每次都必须遵守的执行顺序、停止条件和用户确认点。
- Provider、项目分析和视觉复核等条件性细节放入一层 Reference。
- Reference 之间不相互跳转，避免模型为追踪规则消耗上下文。
- 先按职责拆分；单文件接近 200～300 行时再评估是否继续拆分。
- 同一条决策链保持在同一文件中，不拆成多个过小文件。
- 日常 `d2c` 不依赖脚本；Benchmark 只使用确定性的脚手架重置和预览辅助脚本。

## 4. 组件职责

### 4.1 `d2c/SKILL.md`

负责日常流程编排：

1. 校验输入与目标项目。
2. 检查实际可调用的 Figma 工具并选择 Provider。
3. 读取设计上下文。
4. 读取或建立项目 `D2C.md`。
5. 分析当前页面涉及的代码和资源。
6. 展示实现预览并等待确认。
7. 在确认范围内修改代码。
8. 执行工程验证和视觉复核。
9. 汇总结果、差异和人工验收边界。

### 4.2 Provider References

`provider-official.md` 和 `provider-context-mcp.md` 分别描述：

- 如何识别当前 Provider 的必需工具。
- 如何取得结构、样式、截图和资源。
- 大节点如何分段读取。
- 常见认证、权限、限流及数据缺失错误如何说明。

Provider Reference 只描述工具差异，不产生统一适配层，也不要求保存统一数据格式。

### 4.3 `project-analysis-guide.md`

提供通用分析清单与取证范围，不包含特定公司的结论：

- 项目说明、技术栈、构建工具和路径别名。
- 三方组件库、项目封装组件及页面局部组件。
- Token、主题、样式入口和作用范围。
- 布局、响应式、字体、图片和图标。
- 当前页面需要的数据、交互、路由及验证入口。
- 与当前任务相近的 1～2 个已有页面。

不全库扫描。稳定结论进入 `D2C.md`，页面相关事实在每次任务中现场检查。

### 4.4 `visual-review.md`

保存真实页面验证、多模态分流及 Chrome MCP 定位规则。Chrome MCP 是发现偏差后的定位工具，不是每次执行的固定前置条件。

### 4.5 `templates/D2C.md`

只提供以下空白骨架：

```markdown
# D2C 项目规则

## 技术栈
## 组件使用
## Token 与主题
## 布局与响应式
## 字体与资源
## 数据和交互
## 代码修改边界
## 启动与验证
```

不得预填 React、Vue、Ant Design、Vant 或 E-Space 规则。

## 5. 日常执行流程

```text
输入 Figma URL 和目标项目
        │
        ▼
校验 node-id、项目和 MCP 工具
        │
        ▼
选择并明确提示 Provider
        │
        ▼
读取结构化设计上下文和所需资源
        │
        ▼
读取 D2C.md；首次使用时生成候选内容
        │
        ├─ 首次使用：用户确认 D2C.md 后写入
        ▼
分析相关代码、组件、Token、数据和验证入口
        │
        ▼
展示 ASCII 图与实现预览
        │
        ├─ 用户调整：重新核对相关 Figma 数据并更新预览
        ▼
用户确认后修改代码
        │
        ▼
工程验证 → 真实页面视觉复核 → 条件性 Chrome 定位
        │
        ▼
交付修改、验证结果、已知差异和人工边界
```

### 5.1 输入检查

- Figma URL 必须包含具体 `node-id`，否则停止。
- 目标项目默认是当前工作目录，也可由用户明确指定。
- 目录不是可识别的前端项目时停止。
- 不从整个 Figma 文件中猜测目标 Frame。

### 5.2 Provider 选择

选择顺序为：

```text
用户显式指定 → 官方 Figma MCP → Figma-Context-MCP → 停止
```

- 以当前会话真实可调用的必需工具判断可用性，不依赖 Server 名称或配置文件。
- 两者都可用时默认官方 MCP，并明确告知用户。
- 用户指定的 Provider 不可用或授权失败时停止，不静默切换。
- 用户未指定 Provider、默认官方返回 OAuth 未授权、授权被拒绝或授权已过期，且社区 Provider 可用时，提示后丢弃官方结果并从目标节点改用社区 Provider；其他执行失败不触发切换。
- 不混用两个 Provider 的部分结果。

### 5.3 设计上下文读取

- 写代码前必须取得结构化设计上下文。
- 常规信息包括布局、样式、组件提示和截图；资源按需取得。
- 大节点先读结构，再按主要子节点拆分。
- 官方 MCP 返回的参考代码只表达设计，必须适配实际项目。
- 无法取得结构化内容时停止，不允许只看截图猜代码。

响应式和交互意图的依据顺序为：

```text
用户明确说明
→ Figma 注释、Variants、Constraints
→ 项目已有模式
→ 仍不明确时询问用户
```

已有业务逻辑不会仅因 Figma 表现不同而被覆盖。

## 6. 项目 `D2C.md` 生命周期

### 6.1 首次执行

项目根目录不存在 `D2C.md` 时：

1. 依据通用分析清单检查实际项目。
2. 在对话中展示准备写入的规则。
3. 对无法从代码确认的组织规则询问用户。
4. 用户确认后写入项目根目录。
5. 使用已确认内容继续当前 D2C 任务。

这构成第一次确认。后续实现预览仍需第二次确认。

### 6.2 后续执行

- 优先读取项目已有 `D2C.md`。
- 它由项目团队提交、评审和维护，Skill 不自动更新。
- 与当前代码冲突时，以代码为准，并在实现预览中提示。
- 页面细节、临时兼容、API、路由、权限和埋点不写入该文件。

## 7. 实现预览与变更确认

修改任何项目代码前，在对话中展示：

- 基于实际项目布局的 ASCII 结构图。
- 核心布局、尺寸和间距。
- 字体、颜色、圆角等关键样式。
- 组件计划，并区分三方组件、项目封装组件和页面局部组件。
- Figma 值与项目 Token、变量、主题的映射及影响范围。
- 字体、图片、图标的可用性和候选替代方式。
- 页面数据来源、缺失接口和未明确业务行为。
- 预计修改的文件、组件和样式范围。
- Figma 与项目可访问性规则的冲突。
- 尚不能确定的内容。

展示粒度随任务变化：小组件使用紧凑预览；完整页面给出完整信息；大型页面只绘制顶层结构并按区块摘要。空信息不生成表格，只有冲突项展开对比。

用户提出调整时：

1. 重新检查涉及的 Figma 节点、截图和项目代码。
2. 比较 Figma 原始信息与用户最新要求。
3. 两者冲突时，以用户最新要求为准。
4. 如果用户要求与业务逻辑、项目强约束或安全要求冲突，说明影响并等待决定。
5. 重新展示受影响的实现预览，等待确认。

不得沿用已经失效的组件或 Token 影响判断。

## 8. 实现规则

### 8.1 组件

- 三方组件：不修改依赖源码；使用公开属性、主题、作用域样式或项目包装。仍无法满足时交给用户决定。
- 项目封装公共组件：预览调用方和影响范围，取得明确确认；优先增加向后兼容属性，不改变默认行为。
- 页面局部组件：可在已确认任务范围内修改。
- 已存在 Code Connect 映射时优先使用；创建映射不属于首版。

### 8.2 Token 与样式

分析范围包括 CSS Variables、Less/Sass、JS/TS 主题对象、组件库 Token、Tailwind theme 和项目自定义变量。

作用范围按以下层级识别：

```text
三方库主题 → 项目全局主题 → 公共组件 → 页面或局部组件
```

- Figma 值匹配时复用现有 Token。
- 不匹配时展示来源、现值、设计值、候选方案和影响范围，由用户确认。
- 不为单页还原自动修改全局或公共 Token，优先局部适配。
- 找不到可靠映射时，可在当前页面保留 Figma 原始值。

### 8.3 资源与字体

- 使用 Figma 的真实资源，不用占位图，不根据截图手绘未知 SVG。
- 不为一个图标随意增加图标库。
- 临时下载地址不能进入长期代码；资源落在项目既有资源目录。
- 缺失字体、下载失败或替代资源必须在预览中说明，不静默替换。

### 8.4 数据与交互

- 保留现有业务逻辑。
- 不从视觉稿猜 API、权限、埋点或路由。
- 新页面无真实数据合同时，可用页面范围的静态示例数据呈现 Figma 可见状态，并标明“业务数据待接入”。
- 不为示例数据创建虚假 API、Store、权限或路由设施。
- 用户不接受示例数据时，等待真实数据结构。

### 8.5 可访问性

- 保留语义标签、表单标签、键盘操作、焦点、禁用态和错误提示。
- Figma 表现与项目规则冲突时在预览中说明。
- 只检查本次改动表面，不承诺完整 WCAG 审计。

## 9. Subagent 使用策略

Subagent 是可选的只读分析助手，不是固定阶段。小型任务由主模型完成；复杂页面或影响面较大时，可以把相互独立、范围明确的问题并行交给 Subagent：

- 查找可复用组件及调用方。
- 分析 Token、主题和样式影响范围。
- 查找路由、数据来源和验证入口。
- 在已经确认视觉偏差后收集指定区域的 Chrome 证据。

每个 Subagent 只处理一个问题或一个受限目录，返回证据文件、候选方案、影响、冲突和未知项。首版不允许 Subagent 写代码，也不向其传递凭据。

主模型始终负责：

- Provider 与认证状态判断。
- `D2C.md` 的最终整理和用户确认。
- ASCII 图及整体实现预览。
- 公共组件、Token 和业务边界决策。
- 所有文件写入。
- 视觉结论和最终交付。

高影响结论必须由主模型复查。运行环境不支持 Subagent 时，主模型按同一清单串行完成，不改变结果要求。

## 10. 验证流程

### 10.1 工程验证

验证命令来源优先级：

```text
D2C.md → package scripts、路由和项目说明 → 询问用户
```

按改动范围执行适用的类型检查、Lint、测试和构建：

- 明确由本次修改引起的错误，修复并重试一次。
- 项目历史错误、环境错误和未执行检查分别说明。
- 不修改无关代码，不关闭规则，不降低类型约束来制造通过结果。
- 跳过的检查不能被描述为已经完成。

### 10.2 视觉复核

- 验证目标项目中的真实页面，不用独立日常预览工程代替。
- 从项目脚本、路由和说明确定启动方式；不明确时询问用户。
- 视口匹配 Figma Frame。
- 不为截图修改路由、绕过登录或注入临时业务 Stub。

根据当前会话的实际能力分流：

```text
能读取图片
→ 模型比较 Figma 与真实页面截图
→ 发现偏差后才使用 Chrome MCP 定位

不能读取图片
→ 提供 Figma 参考和真实页面入口
→ 等待用户指出偏差
→ 再使用 Chrome MCP 定位
```

不按模型名称维护多模态白名单，也不用 DOM 数值替代视觉判断。用户只说“有问题”时，先确认区域或问题类型。

Chrome MCP 只检查相关元素的尺寸、盒模型、计算样式、父级布局及对应源码。DevTools 临时修改只用于诊断，最终修改必须落到源码。修正后只复核一次，剩余差异交给用户决定，不自动循环。

## 11. 错误和会话语义

- 临时超时、限流或资源下载失败可以安全重试一次。
- OAuth、Token、权限、设计范围和业务取舍由用户决定；Provider 只在默认官方返回 OAuth 未授权、授权被拒绝或授权已过期的固定分支提示后切换。
- 除上述固定 OAuth 分支外，Provider 失败后不自动降级；所有分支都不混用部分数据。
- 未取得结构化设计上下文、未确认预览或未完成代码写入时，不把部分结果当成交付完成。
- 同一会话可从已确认预览继续；新会话或需求发生变化时重新分析。
- 不生成恢复文件。跨会话的稳定项目知识只来自 `D2C.md`。

## 12. Benchmark 设计

### 12.1 目的

Benchmark 只让用户直观看到当前模型对不同页面类型的还原结果，不判断“通过”或“适合哪类任务”。用户在本地使用当前模型运行，不做模型选择或横向排名。

### 12.2 固定场景与技术栈

一次执行四个稳定 Figma 节点：

1. PC 数据管理页：React + TypeScript + Ant Design。
2. PC 图表分析页：React + TypeScript + Ant Design。
3. 移动端内容展示页：Vue 3 + TypeScript + Vant。
4. 移动端表单交互页：Vue 3 + TypeScript + Vant。

图表库在脚手架中预装且固定，具体选型在实现脚手架前确认。场景使用本地模拟数据，不接后端。模型不得替换或增加基础组件库、图表库。

### 12.3 执行与确认差异

Benchmark 复用日常 `d2c` 的 Provider、设计读取、代码生成、工程验证和真实页面原则，但有一个明确例外：

- 输出写入隔离脚手架，不修改业务项目。
- 因此不为四个场景逐一展示实现预览或等待确认。
- 一次完成全部场景后，用户在统一预览入口自行判断。

每个场景从相同干净基线开始且结果互相隔离。单场景失败不阻塞其他场景；MCP 或脚手架整体不可用时停止。每次只保留最新一轮结果。

### 12.4 统一预览

预览页面含四个标签页。每个标签页左侧显示 Figma 原始设计，右侧嵌入真实、可交互的页面：

- 页面宽度与 Figma Frame 一致。
- 长页面纵向滚动。
- 移动端按设计设备宽度展示。
- 失败场景展示原因。

不展示分数、阈值、通过状态、排名或能力等级。

## 13. 测试与验收

### 13.1 静态检查

- 主 Skill 的流程顺序和停止条件完整。
- Reference 为单层引用，无循环和缺失链接。
- Provider 规则中不存在静默切换或凭据读取。
- `D2C.md` 模板不包含项目特定结论。
- 日常 Skill 不依赖执行内核或中间状态文件。

### 13.2 场景检查

覆盖以下分支：

- URL 缺少 `node-id`。
- 仅官方 MCP 可用、仅 Context MCP 可用、两者均可用、两者均不可用。
- 用户指定 Provider 不可用或认证失败。
- 首次执行缺少 `D2C.md`。
- 用户调整实现预览，且要求与 Figma 冲突。
- 修改项目公共组件或全局 Token。
- 字体、图片或图标缺失。
- 当前模型不能读取图片。
- 视觉偏差存在但 Chrome MCP 不可用。

### 13.3 真实项目验收

至少验证：

- 一个 React + TypeScript + Ant Design 项目。
- 一个 Vue 3 + TypeScript + Vant 项目。
- 官方 Figma MCP 与 Figma-Context-MCP 各一次完整流程。
- 首次执行在两次确认前不产生对应的项目规则或业务代码写入。
